# ساخت برنامه و آماده‌سازی برای پروگرام

پروژهٔ `lesson-06-project-v2.zip` را استخراج کنید. در حلقهٔ اصلی، داخل بلوک موجود USER CODE 3، تغییر وضعیت PB6 و سپس `HAL_Delay(500U)` قرار دارد. LED کاربر برد GB100ST V2.0 از طریق درایور NPN با High روشن می‌شود. 2 تغییر وضعیت یک چرخه می‌سازند؛ انتظار اسمی حدود 1 Hz است. این رفتار روی برد مشاهده نشده است.

## ساخت در رایانه

از ریشهٔ پروژه با CMake 3.22 یا جدیدتر، Ninja و arm-none-eabi-gcc:

```text
cmake --preset Debug
cmake --build --preset Debug --clean-first
cmake --preset Release
cmake --build --preset Release --clean-first
```

اینها فرمان‌های پروژهٔ CMake هستند. برای مسیر CubeIDE از IOC کپی جدا بگیرید و خروجی مناسب IDE را تولید کنید؛ متادیتای بومی Eclipse در این ZIP نیست و واردکردن یا ساخت گرافیکی آن آزمایش نشده است.

در بازبینی 2026-11-02 هر دو ساخت پاک، با سورس بدون تغییر و GCC 13.2.1 بدون هشدار انجام شدند. پرچم‌های C در Debug برابر `-O0 -g3` و در Release برابر `-Os -g0`، با `-Wall -Werror` هستند. اینها پیش‌فرض همهٔ IDEها نیستند. پروژه با CubeMX 6.14.0، پایگاه 6.0.140 و F3 V1.11.6 تولید شده و SYSCLK نامی HSI برابر 8 MHz است؛ کریستال‌های خارجی فعلاً فقط پایهٔ رزروشده دارند.

## کدام فایل را استفاده کنیم؟

`lesson-06-build-artifacts-v2.zip` خروجی‌های واقعیِ قبلی همین سورس تأییدشده را در پوشه‌های Debug و Release نگه می‌دارد. گزارش‌های ساخت مجدد تازه‌اند؛ آرشیو خروجی‌ها با نسخهٔ تأییدشدهٔ قبلی یکسان است و تازه‌دریافت‌شده از ساخت مجدد معرفی نمی‌شود.

ELF قالب ساختاریافتهٔ برنامه، HEX متن دارای آدرس، BIN تصویر خام و MAP گزارش متنی لینکر است. MAP را پروگرام نکنید. BIN خام نشانی بارگذاری ندارد؛ پایهٔ Flash این پروژه `0x08000000` است. CMake فایل‌های HEX و BIN را با objcopy از ELF می‌سازد. Verify برنامه‌ریزی فقط تطبیق محتوای خوانده‌شده و فایل را نشان می‌دهد، نه درستی منطق برنامه.

Flash در Debug برابر 8112 و در Release برابر 3688 بایت است. RAM در هر دو 1584 بایت است: data برابر 12، BSS برابر 32، هم‌ترازی 4، رزرو heap برابر 512 و رزرو stack برابر 1024 بایت. اندازهٔ فایل ELF روی دیسک با مصرف Flash برابر نیست. Release با وجود پرچم C یعنی `-g0` هنوز بخش `debug_info` به اندازهٔ 576 بایت دارد؛ وجود اطلاعات دیباگ کل فایل به همهٔ اجزای لینک وابسته است. این اعداد اندازه‌گیری مصرف اوج زمان اجرا نیستند.

## بررسی فایل‌ها و مشاهدهٔ خودتان

Python 3 را کنار فایل‌های همین بسته اجرا کنید:

```text
python verify_blink_artifacts_v2.py
```

مدل، سورس و هش‌ها، قالب واقعی ELF، checksum رکوردهای HEX و برابری محتوای HEX با BIN را بررسی می‌کند. نتیجه در `blink-artifact-results-v2.json` می‌آید. در HAL همین نسخه، درخواست 500 ms آستانهٔ 501 تیک دارد؛ این به معنی تأخیر فیزیکی دقیق 501 ms نیست. فاز تیک، خطای کلاک و وقفه‌ها اثر دارند. هیچ مشاهدهٔ برد یا شناسایی هدف در این دستور انجام نمی‌شود.

`build-comparison-worksheet-v2.csv` برای ثبت ساخت خودتان و `programming-observation-worksheet-v2.csv` برای مشاهده‌های واقعی شماست؛ همهٔ وضعیت‌ها در انتظارند. پیش از اتصال، مدل دقیق پروب و راهنمای آن را بشناسید. SWDIO به PA13، SWCLK به PA14 و زمین مشترک لازم‌اند؛ مرجع ولتاژ هدف و NRST طبق راهنمای همان پروب و برد بررسی شوند. برای Under Reset، اتصال NRST لازم است و این روش درمان تضمینی همهٔ خطاها نیست.

ورودی نامی 5 V برد با ریل نامی 3.3 V تراشه و مرجع VAPP/VTref یکی نیست. مرجع هدف را خروجی تغذیه فرض نکنید و دو خروجی تغذیه را به هم نبندید. UM1075 Rev 10 می‌گوید ST-LINK/V2 استاندارد حتی برای هدف با ولتاژ پایین‌تر، سیگنال‌های خروجی 3.3 V دارد؛ وجود VTref تضمین تبدیل خودکار سطح در همهٔ پروب‌ها نیست. شمارهٔ هدر یک پروب را به نمونهٔ دیگر یا هدر برد تعمیم ندهید.

Option Bytes در این درس فقط برای خواندن و ثبت است؛ RDP را تغییر ندهید. سطح 2 در F303 برگشت‌ناپذیر است و بازگشت سطح 1 به 0 با پاک‌شدن Flash همراه است. برای انجام‌نداده‌ها شاهد موفقیت نسازید: پروگرام، Option Bytes، اتصال هدف، اجرای CubeIDE و اندازه‌گیری زمان در این بررسی انجام نشده‌اند.

نسخه‌ها و هش‌ها در `toolchain-and-validation-v2.json`، منابع در `sources-v2.json` و کد شاهد در `source-evidence-v2.txt` هستند. مجوزهای اصلی ST و Arm داخل ZIP سورس حفظ شده‌اند.
